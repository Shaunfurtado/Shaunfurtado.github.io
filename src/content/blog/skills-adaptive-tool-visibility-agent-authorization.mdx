Ananta's agent has 126 native tools: 29 for building alert workflows, 26 for broker data, 19 for the workspace canvas, 18 for the browser, 8 for the sandbox, and a long tail. On top of those come market-data operations from MCP servers (one exchange MCP server alone exposes 36 tools), connectors built for a specific client's own systems, and calculator extensions. Depending on the deployment, that's well into the hundreds.

Sending all of them on every call is expensive and confusing for the model. Sending only a few makes the agent helpless at the first unexpected question. Here's how we handle it, and what measuring it taught me.

## Layer one: permissions decide what exists

Before any routing, the tool list is filtered by the user's role. Required permissions come from the tool's name prefix — a deliberately simple scheme you can read in one function:

```python
tool_permissions("web_fetch")         # {"chat.use", "research.web"}
tool_permissions("sandbox_run_python") # {"chat.use", "analysis.sandbox"}
tool_permissions("broker_get_quotes")  # {"chat.use", "market.view",
                                       #  "broker.view", "broker.use_data"}
tool_permissions("subagent_run")       # {"chat.use", "research.deep"}
```

Alert-writing tools need `alerts.manage`. Anything that exports or shares needs `chat.share`. A tool the user can't use is removed before routing and before discovery. The model never sees it and can't search for it. The system prompt also gets a short note about what's restricted, telling the model not to promise, simulate, delegate, or work around those capabilities.

The trade-off is that prefixes make rules easy to read and also easy to forget: a new tool has to be named into the right family, and that's something review has to catch.

## Layer two: a route picks a stable profile

Tool profiles are on by default. Each run is classified into one of nine routes: simple chat, market read, alert workflow, saved workflow, browser read, browser research child, artifact builder, workspace editor, and deep research parent. Each route has a fixed set of tools. On top of that sits a stable core of ten control tools that every parent run gets: `ask_user`, `present_chat_block`, `skill_catalog`, `skill_load`, `session_search`, `session_expand`, the plan tools, and `extension_propose`.

Routes add to that rather than replace it: tool hints from a loaded skill, the full catalogue of a market-data MCP server (never a hand-picked subset — partial MCP catalogues confused the model more than they helped), lexically related tools (top six above a similarity floor), and any extensions the user mentioned by name. Every run emits a `tool_profile_selected` event listing exactly what was attached and why.

Routes go wrong in boring ways. "Looks good, turn it on" after building an alert was routed to simple chat with no tools. The agent then searched for and reloaded the same alert tools on every follow-up — about a quarter of all tokens in the alert-authoring chats we traced. Now an active alert-building session keeps its route. Separately, "include their earnings as well" after an answer-only question lost its market tools, because answer-only defaulted to simple chat. The default is now market read.

## Layer three: load what's missing, on demand

When a route doesn't have what's needed, the agent has four capability tools: search, load, list groups, and load group. Search returns at most eight results with 220-character summaries. Load takes up to eight exact names and is all-or-nothing.

```python
def capability_load(names: list[str]) -> dict:
    if len(names) > 8 or any(n not in run_inventory for n in names):
        return {"code": "capability_unavailable", "retry": False,
                "note": "Not in this run's authorized inventory. Do not retry."}
    attach(names)
    return {"note": "Available on the next model step. Nothing was executed."}
```

The inventory is per run, immutable, already filtered by permissions, and versioned by a hash. A load against a stale version gets `catalog_version_changed`. Loaded tools attach on the *next* model step and are appended to the end of the list, never re-sorted, for reasons covered in [the prompt caching post](/blog/prompt-caching-ai-agents-prefix-cache-hit-rate/). Loaded names are saved in run metadata, so a resumed run gets the same tools back. For self-hosted models with small windows, a schema budget evicts older tools, and if even the requested tools don't fit, the agent is told so.

The tool messages say "loading is discovery, never execution" more than once. Models do sometimes believe that loading a tool did the thing.

## The guard on every call

Visibility doesn't grant anything. Every tool is wrapped, and the wrapper re-reads membership fresh — there's no process-wide permission cache — before running it. If the user's workspace access changed since the tools were attached, the call is refused. It checks file and resource provenance, information-barrier rules on any workflow, session, or run being read, and whether the arguments mention a restricted security.

Then it checks the *output* too. A broad search can return a restricted company without anyone having named it. If a desk is walled off from a security, the result is refused before the model sees it. No skill and no capability load grants access to anything. They only decide what's convenient to reach.

## Skills are procedures, versioned and reviewed

There are 23 shipped skills: markdown files with a name, a "use when / don't use when" description, a version, tool hints, keyword triggers, and optionally a spawn block for delegation. The skill catalogue in the prompt is capped at 2,000 characters, a loaded skill body at 12,000, and at most four skills auto-load from triggers. Skill bodies go at the end of the model input, after the conversation, to keep the cached prefix stable.

Skills can be improved, carefully. In our October evaluation the model activated a skill override when the user had only asked for a draft. Proposals now stay inactive until a person activates them. Later we added an opt-in where the owner can let independently reviewed revisions apply automatically — but only to allowlisted methodology skills, and never to tool hints, triggers, or delegation settings. The approval is bound to a fingerprint of the revision and hashes of the paired test outputs. Edit the revision and the approval is gone.

## The experiment where loading less cost more

The obvious next step was to make deferred loading the default: attach a small core and let the agent load the rest. We tested it properly, on frozen inputs, with the same conversation replayed against two strategies.

Deferred loading cut serialised schema bytes by 28%, from about 217 KB to 157 KB. But the full strategy used 73,598 input tokens across 2 calls in 49 seconds. Deferred used 74,415 tokens across 4 calls in 61 seconds. The extra round trips to discover and load tools cost more than the smaller schemas saved — and in an earlier run, selective loading had halved our cache coverage before we fixed the tool ordering.

So nothing was promoted. Production attaches the full tool set for the selected route, in a stable order, and capability loading is the escape hatch rather than the main path. Route profiles do most of the work. We also tried embedding-based tool retrieval and removed it: worker processes start fresh, so loading the embedding model on each worker's first tool call cost more memory and startup time than the retrieval was worth. Related-tool matching is lexical now.

The lesson I keep coming back to: the number to optimise is input per *completed task*, not bytes per request. The two moved in opposite directions.

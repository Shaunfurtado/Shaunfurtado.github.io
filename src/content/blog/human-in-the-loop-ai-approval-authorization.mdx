Ananta connects to people's broker accounts. The obvious feature request is "let the agent place the trade after I approve it". We haven't built it, and that decision shapes everything else in this post.

No agent tool places, modifies, or cancels an order. Broker tools are reads, plus watchlist edits. The REST endpoints for order mutations aren't in the public API schema, and they refuse unless an operator has explicitly turned on order mutations for the deployment *and* the caller is an admin. Children are told in their prompt never to touch the broker. For actions that move money, the human-in-the-loop design is: the human does it.

Everything below is about the actions we *do* let the agent take, and the four approval mechanisms that guard them.

## The month approval was a chat message

I'll start with the mistake, because it's the most useful part.

From late September to late October, approving an alert workflow deployment went like this. The agent showed a card with "Deploy" and "Keep as draft". Clicking Deploy sent a hidden chat message back to the agent — something like "HITL: Deploy this workflow. I confirm confirm=true. Do not list approval options again." — and the *model* then called the deploy tool with `confirm=true`.

It mostly worked. It was also an approval system whose final step was a language model reading a sentence and deciding what it meant. The approval wasn't tied to a specific workflow version, a model could misread it, and nothing stopped a model from producing `confirm=true` without the click.

In October we moved it to the server. The card's buttons now call an authenticated endpoint that performs the action itself — the click *is* the confirmation. The deploy tools still refuse without `confirm=true` and return `confirmation_required` with a card, but the card no longer routes through the model. A shared analysis link never authorises a deployment, even for someone who can see it. After deploying, the endpoint reads the workflow back and returns 409 unless it's actually active. The outcome is recorded in the run's metadata and as an event.

A day later a real-browser test turned up a race. The user approved a draft mid-run, and the agent's next edit overtook it: "Kept as draft", then a new review card. Cards from a run that's still going are now shown as *waiting* and only become actionable when the run finishes. Card states: pending, resolved, superseded by a newer review of the same workflow, expired, and waiting.

## Questions: the first answer wins, silence decides nothing

When the agent needs input mid-run, it calls `ask_user`. The wait is capped at 30 seconds. The question id is derived from the run, its epoch, and the tool call id, so a retried tool call asks the same question rather than a new one. Answering is a compare-and-swap:

```sql
UPDATE chat_questions
   SET status = 'answered', answer = :answer
 WHERE id = :id AND status = 'pending'
   AND expires_at > now() AND run_epoch = :epoch;
-- rowcount != 1 → "Another answer already resolved this question"
```

The comment on that query notes that the compare-and-swap protects SQLite too, where `SELECT … FOR UPDATE` does nothing. Two tabs, two clicks, one answer.

There's no default answer. If nobody answers, the agent is told that silence doesn't select a deliverable or authorise any action. In our October evaluation one scenario let a question expire on purpose. The older code had treated expiry as permission to pick a default. Now the late answer gets a 409.

## Extensions: approve exactly what was tested

The agent can propose a new calculator extension — source code plus test fixtures — and the sandbox evaluates it. Passing the evaluation doesn't enable it. The owner gets an approval card, and that approval is bound to the exact extension id, version, and evaluation report id, and only if the evaluation passed. If anything changed between evaluation and approval, enabling returns 409: "Extension changed; review a fresh proposal before enabling."

Planning mode, child runs, and test automation can't enable a proposal. Test automation, for what it's worth, is gated to designated test users, can only auto-approve alert deployments, and records each one as `test_automation_approval` — explicitly labelled as not human authorisation.

## Connector write-backs: prepare, ask, re-check, send

Some client deployments have connectors that can write to the client's own systems — update a record, post a note. This is the most complete approval flow we have:

1. **Prepare.** Validate the payload against the action's JSON schema, canonicalise it, derive an idempotency key from the run, user, and canonical payload, and insert a row in `pending_confirmation`. If the key already exists, return the stored result marked `reused`.
2. **Ask.** "Send to X: … ?" with *Send* and *Don't send*, and no recommended option.
3. **Confirm.** Compare-and-swap from `pending_confirmation` to `confirmed`.
4. **Re-check.** Permissions and information barriers are evaluated again, fresh.
5. **Claim.** Compare-and-swap from `confirmed` to `sending`.
6. **Act.** Call the connector with the idempotency key.
7. **Record.** `sent` or `failed`, plus an audit receipt.

It refuses outside an interactive chat — "confirmation unavailable; nothing was sent" — so scheduled runs and children can only read. Automated test answers don't count, because the confirmation must come from a user.

## The browser: approval hands over control

In the browser plane, actions are classed from R0 (observe) to R4 (prohibited). Version one denies everything consequential — R3 and R4 — in code. If someone clicks approve on one anyway, the request is recorded as denied with `forced: true` in the audit log.

Approving a takeover or a login request doesn't let the agent carry on. It hands control to the *person*: the identity's control epoch is bumped, the browser broker fences the session at the new epoch, the agent's lease is cleared, and any agent command still in flight fails because its epoch is stale. ([The browser post](/blog/browser-agents-identity-infrastructure/) covers that fencing in detail.)

## Who's allowed to approve

All of this sits on role-based access with four built-in roles — admin, operator, viewer, and pending/disabled — plus custom roles, and per-member monthly spend limits with a notice at 80% and a stop at 100%. Information barriers add desks with symmetric walls and restricted securities. Admins get no read bypass. A member restricted from a security doesn't get streamed tokens at all, because a ticker can be split across stream fragments; their answer is screened whole before it's stored.

## What's still not right

The four mechanisms grew separately, and they aren't equally strict yet. Extension approval is bound to an exact version and evaluation report. Deploy approval is newer and simpler, and bringing it up to the same standard is next. The connector confirmation shows each field cut to 60 characters, which is readable but easy to skim past. And `ask_user` keeps the worker polling for its 30 seconds — bounded, but not free.

The pattern I'd recommend is the one we arrived at late: the approval is a row on the server, the click resolves that row, and the model is told what happened afterwards. If the model is in the path between the human's click and the action, you don't have approval. You have a suggestion.

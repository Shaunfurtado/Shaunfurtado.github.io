Redis does a lot of different jobs in Ananta: instrument search cache, latest-quote cache, a write-behind buffer for quotes, RQ queues, live tick streams for alerting, leases, and wake-up hints for server-sent events. For a while it did all of them in one instance with one configuration, which meant the configuration was wrong for most of them.

## Split by what you're allowed to lose

The fix was to stop thinking of Redis as one thing. In the Postgres deployment there are two instances with opposite rules:

| | `redis-cache` | `redis` |
|---|---|---|
| Holds | instrument search results | queues, streams, leases, quote buffer |
| Memory | 192 MB, `allkeys-lfu` | 512 MB, `noeviction` |
| Persistence | none | AOF, `appendfsync everysec` |
| If it's wiped | slower searches | lost work, unless SQL has it |

The cache can evict anything at any time, and losing all of it costs some latency. The other instance must never evict — an evicted queue entry is a run that silently never happens — so it refuses writes when full, and that's an alert, not a degradation. Putting both workloads under one `maxmemory-policy` means one of them is always configured wrong.

## A cache key is part of the permission model

The quote cache key looks like this:

```text
ananta:quote:v2:<db fingerprint>:<user>:<account>:<broker>:<EXCHANGE>:<SYMBOL>
```

Every segment is URL-quoted, so a strange symbol can't break out of its tenant during a `SCAN`. The database fingerprint means two deployments accidentally sharing a Redis can't read each other's keys. User and account are in there because quotes come through a user's own broker connection, and one user's entitlement shouldn't become another user's cache hit. A comment in that module says what's deliberately *not* in the key or value: no broker credentials and no cross-account aliases.

## Refusing older observations

Quotes arrive from several places — a live feed, a REST poller, a batched fetch during a scheduled workflow — and they don't arrive in order. A naive `SET` lets a slow poller overwrite a newer tick with an older one. So writes go through one Lua script:

```lua
-- KEYS: quote, clock, pending, dirty   ARGV: json, ts
local last = tonumber(redis.call("GET", KEYS[2]) or "0")
if last > tonumber(ARGV[2]) then return 0 end      -- older than what we have
redis.call("SET", KEYS[1], ARGV[1], "EX", 30)       -- latest quote, 30s
redis.call("SET", KEYS[2], ARGV[2], "EX", 604800)   -- clock, 7 days
redis.call("SET", KEYS[3], ARGV[1], "EX", 604800)   -- pending copy for SQL
redis.call("ZADD", KEYS[4], ARGV[2], KEYS[3])       -- mark dirty
return 1
```

The pending copy and the dirty set are a write-behind buffer. A separate process flushes dirty quotes to SQL snapshots, and acknowledges with another script that only deletes the pending copy if its bytes haven't changed — so a flush can never erase an update that arrived while it was writing.

Ingestion also rejects zeros and errors. A missing or zero price isn't a market observation, and caching it means an alert might fire on "price fell to 0".

The client side is deliberately impatient: a 0.3-second connect timeout, 0.5-second socket timeout, no retries, and a five-second local circuit after a failure. If Redis is slow, the caller still gets the direct broker result. Retrying a cache read only adds load to something that's already struggling.

## One evaluator, a fenced checkpoint

Live alerting reads ticks from per-account Redis Streams (`live:ticks:<user>:<account>:<broker>`, capped at about 2,000 entries). We don't use consumer groups. Exactly one evaluator process owns all the streams, through an owned lease with a 15-second TTL, and reads with plain `XREAD`.

Progress is a checkpoint key per stream, written by a Lua script that refuses if the caller no longer holds the lease or if the offset would move backwards. Evaluator state is keyed by the owner's token, so an old process that wakes up after losing its lease can't corrupt the new owner's state.

If the oldest entry still in the stream is newer than our checkpoint, the stream was trimmed past us and we've lost ticks. The evaluator treats that as a continuity break and starts a new epoch, so a rolling window or a "crossed above" condition isn't computed across a gap it can't see.

## Leases are an optimisation; SQL fences

Every lease in the system is `SET NX EX` with a random token, renewed and released only by Lua compare-and-set scripts. A `GET` then `EXPIRE` from Python can extend the *next* owner's lease if yours expired in between.

A Redis lease still isn't a lock you can bet money on. A process can pause for longer than its TTL. So wherever correctness matters, SQL has the final say: runs carry an attempt and an epoch, and scheduled jobs are claimed with a compare-and-swap on the whole row. The scheduler's leader lease only decides who bothers to check. As one comment puts it, the database decides who owns a due row.

## Streams as hints, SQL as truth

Chat events are written to SQL. Redis gets a much smaller `XADD` with only the sequence number, event type, and id — enough to wake up anyone streaming that run to a browser. If the `XADD` fails, we stop sending hints for 15 seconds and readers fall back to polling SQL.

The SSE reader takes the stream tail *before* it reads from the database. Anything committed concurrently is then either in that read or in the next `XREAD`, so nothing slips between the two. SQL reads are capped at five per second per viewer, connections have a bounded lifetime so a reconnect re-checks authorisation, and a terminal status in SQL ends the stream even if the terminal event's hint was lost.

Notification streams go further: every notification is re-read from SQL before it's sent, and old Redis payloads are never replayed.

## Things that went wrong

**Blocking reads on threads.** The first SSE implementation used synchronous `XREAD` inside `asyncio.to_thread`. With a few dozen viewers, each five-second blocking read held a thread and competed with unrelated work. Moving to `redis.asyncio` fixed it. A later test with 50 notification viewers showed zero idle database transactions.

**An evaluator a minute behind.** In October the alert evaluator was running about 57 seconds behind the quote stream — roughly 35 ticks a second coming in against a capacity of about 37. Ticks older than 60 seconds are skipped on purpose, so we were close to silently missing alerts. The cause was re-parsing each matching workflow's rule definition, and re-querying instrument metadata, on every tick. Caching the parsed plan per saved revision, and instrument scope for an hour, brought it back to real time.

**A lease held by an exception.** A connector without credentials raised an error before the code that releases its sync lease. The lease stayed held, no error was recorded, and the connector just stopped syncing. We found it on a live rollout. Now that path records the error and gives the lease back like any other failure.

The common thread: each pattern in Redis needs a sentence saying what happens when its data disappears. If you can't write that sentence, it shouldn't be in Redis — or SQL should be holding the real copy.

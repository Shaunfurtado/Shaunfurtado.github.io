People are sometimes surprised that Ananta's agent runs go through RQ. No Celery, no Temporal, no managed queue. Just Redis lists and Python workers.

The reason is the deployment model. Each client runs the whole stack on their own server, often looked after by someone who isn't a distributed-systems person. RQ is something I can explain in one diagram, and Redis is already in the stack. The trade is that RQ gives you very few guarantees, so the guarantees we need live in our code and in SQL.

Here's what that looks like after a few months of production traffic and one fairly expensive evaluation.

## The job is just a pointer

An RQ job in Ananta carries one thing: a `run_id`. The function path is fixed, the job id is deterministic (`broker-chat-<db fingerprint>-<run_id>`), and everything the run needs — the user's message, the model, the session, the tool policy — is in SQL.

Before anything touches Redis, the API writes a `RunDispatchRecord` row saying which queue (we call it a lane) admitted the run. The SQL session is closed before any Redis I/O, so a slow Redis can't hold a database transaction open.

That ordering is the whole point. During one test we stopped Redis, submitted a run, and the API admitted it in under half a second. When Redis came back, the run dispatched about four seconds later, with exactly one model call recorded. The intent lived in SQL, so there was nothing to lose.

## We don't use RQ's retries

There's no `Retry(...)` on our jobs and no RQ timeout either — `job_timeout` maps to `-1`. That looks reckless until you see what replaces them.

Retries of model calls are owned by the agent harness, which knows the difference between a rate limit and a quota error and a malformed tool call. The harness also enforces its own absolute deadline, which never slides forward when a job is extended. RQ's death penalty, by contrast, kills a job with no idea whether a model call was mid-flight.

Re-dispatch is a reconciler:

```python
def ensure_queued(run_id):
    job = fetch_job(job_id_for(run_id))
    if job is None:
        return enqueue(run_id)
    if job.status in {"failed", "finished", "stopped"}:
        job.delete()
        return enqueue(run_id)
    if job.status == "queued" and redis.lpos(queue.key, job.id) is None:
        queue.enqueue_job(job)   # metadata says queued, list says otherwise
```

That last branch caught a real case: RQ's job hash said "queued", but the job id wasn't in the list any more. Because the job id is deterministic, running the reconciler twice is harmless.

Each run also carries an `attempt_id`, the id of the owning worker, and a run epoch. A worker that lost its lease can't write results for an attempt that has moved on.

## SimpleWorker, in its own process, with two heartbeats

We run RQ's `SimpleWorker` — no fork per job — but each worker is its own child process spawned by a pool parent. Forked workers inherit database connection pools, which is a well-known way to get two processes talking over one Postgres socket. With `SimpleWorker` in a fresh process, a worker owns its pools for its whole life.

Each worker runs two independent daemon threads that beat every five seconds: one for worker readiness and one for the current job's execution. The job heartbeat is stopped *before* RQ removes the execution metadata — the other order would briefly bring a finished job back to life.

Children import the model SDK and the full tool registry *before* registering with RQ. A warm worker shouldn't make the user's first chat pay a multi-second cold start.

## Children must not borrow parent capacity

An agent can delegate to child runs. Parents go on one queue, children on another, workflow-editor turns on a third. For a while we allowed work stealing between them, because idle capacity is wasteful.

Our October evaluation found the problem. A parent waits for its children while holding its worker. Child workers, allowed to steal, picked up more parents. Once the pool was saturated, every slot held a parent waiting for a child that had no worker to run on. The fix was one parameter: child workers always listen only on the child queue. Work stealing still exists, off by default, and it never lends child slots.

Fairness is a small piece of code too. Pending jobs are reordered round-robin by user under `WATCH`, so one person submitting thirty runs doesn't stall everyone else. If anything changes the list during the reorder, the transaction aborts and we try again later rather than overwrite a job someone else just accepted.

## Queues pinned to a build

This is the newest part and it came from a deploy-time bug. With execution generations turned on, each lane name carries a hash of the runtime source:

```text
broker-chat:<db fingerprint>:runtime-<source sha256>
```

A run admitted by build N runs on build N. We never want a half-deployed system where a new worker picks up a run admitted under old code and interprets its stored state differently.

Then, in late October, a chat turn admitted just before a deploy waited forty minutes on a lane that no worker served any more — the old build was gone. It also blocked that session's next message, since turns within a session run in order.

The fix re-pins queued runs that *never started* when no worker with a heartbeat from the last three minutes is listening on their lane, and the reconciler now runs every two minutes rather than only at startup. Two follow-ups landed the same day: runs reset after an expired attempt are covered too, and moved runs get the current build manifest stamped on them, otherwise the new worker rejects them as a build mismatch. A run that has *started* is never moved. That one fails closed for an operator to look at.

## Cron isn't RQ either

Scheduled workflows don't use `rq-scheduler`. They use a compare-and-swap in SQL plus a Redis leader lease. The lease (45 seconds, renewed every 15) only decides which process bothers to look. The database decides who owns a due row: the claim `UPDATE` matches the full tuple of id, next fire time, cron expression, timezone, misfire policy, owner, and lease.

Advancing the schedule and inserting an occurrence row happen in one commit. The occurrence then moves through `claimed → dispatching → ok | error | skipped`. A row stuck in `dispatching` for more than five minutes becomes `unknown`, with a note that side effects are uncertain and weren't replayed. The docstring says outright that this isn't exactly-once external delivery. I'd rather have that sentence in the code than a guarantee we can't keep.

If someone edits or pauses a workflow after an occurrence was claimed, the old occurrence is marked skipped, so yesterday's claim isn't run with today's configuration.

## Where it hurt

A burst test of 250 runs from 50 users on 16 slots: all 250 admitted in 8.6 seconds, then 490 seconds to drain, with a p95 wait of 423 seconds. Our gate was 120 seconds, so it failed, and we wrote it down as failed. (The first attempt only admitted 249 of 250, because the test lab used a five-second database pool timeout instead of twenty.)

A maintenance queue for market-data repair grew past 37,000 pending jobs. Ordinary refreshes sat behind it and the upstream provider started returning 429s. We split refresh and repair into separate queues, coalesced repair ranges per scope, and added a shared cooldown after a 429.

None of these were RQ's fault. RQ did exactly what it promises, which isn't much. The bugs were in what we assumed on top of it, and the fixes were all about writing those assumptions into SQL where we could check them.

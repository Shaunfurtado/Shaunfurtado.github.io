Most autoscaling advice assumes a cluster: add nodes, let an HPA watch a metric, done. Ananta runs on one client's machine. There is no next node. Every worker we add competes for the same RAM as the browser sessions, the code sandbox, Postgres, and the client's own processes.

So our scaling problem isn't really "how many replicas". It's "how much work can this box take right now without hurting something else", answered every second, by code that has to be right when the numbers it reads are wrong.

When I first wrote about this, I described scaling on queue age. That's not what we ended up doing, and the reason is worth explaining.

## Running processes aren't ready capacity

Agent runs execute on RQ workers. A parent process in each worker container spawns children — each one a separate `python -m` process, not a fork after import — and each child runs one worker.

The first version scaled on queue depth versus process count. It over-counted constantly. A process that's spawned but still importing the model SDK and tool registry (a few seconds, and a lot of memory) isn't capacity. Neither is a process that's alive but wedged. So the pool asks RQ which workers are registered and idle, matching on hostname *and* pid — pid alone collides between containers — and counts three groups: ready and idle, busy, and starting.

```python
pending = depth - ready_idle - starting
target = max(floor, active + pending)
target = min(target, cpu_cap, active + memory_slots)
```

Children preload the heavy imports *before* they register with RQ, so "ready" really means a chat won't pay the cold start. The parent wakes on a Redis `BLPOP` hint when work arrives, waiting at most a second, and spawns at most five processes per tick, because imports allocate memory before the cgroup sample shows it.

## Limits come from the cgroup, not the host

Inside a container, `os.cpu_count()` tells you about the host, which is the wrong question. The CPU cap reads `cpu.max` and multiplies by an oversubscription factor (agent runs spend most of their time waiting on the model, so a core can carry several). Memory slots come from `memory.max − memory.current − reserve`, divided by about 384 MiB per worker.

One rule in that code matters more than the formulas: if queue telemetry fails, the answer is *unknown*, not *empty*. A Redis timeout used to look like a quiet queue, the idle timer would start, and five minutes later we'd scale down in the middle of a busy period. Now an unreadable queue holds current capacity and doesn't start the idle clock.

## Scaling down is a drain, never a kill

Scale-down sends one SIGTERM. In RQ that means "finish the current job, then exit". We never send a second signal. An agent run can take several minutes, and killing it halfway turns a capacity decision into a user-visible failure with uncertain side effects. (On Windows, SIGTERM is a kill, so in development there's no drain at all — which once had me debugging "lost" runs that were really just my laptop.)

There's also a drain file. Touching `/tmp/ananta-execution-drain` sets the target to zero, which is how deploys empty a container politely.

## The host controller

Above the in-container pools there's a small host-level controller, running as a user systemd service, that decides how many worker *containers* exist. It's allowed to scale exactly three services and nothing else.

Each tick it reads demand — only workers with a heartbeat in the last 15 seconds count — and computes slots from the host's available memory, after leaving room for the full sandbox and browser reservations plus 20% headroom. Slots are shared out by weighted fair rounds, with reservations for chat, workflow, and subagent work, and busy work is never taken away because an estimate dropped. A lower target has to hold for five minutes before it applies.

Removing a container is careful in a way Compose can't be. Compose won't let you choose *which* replica goes, so the controller checks through `docker exec` that a replica's workers aren't busy, touches its drain file, waits for them to deregister and for any preloading children to finish, and only then stops it with a 90-second grace. Before any of that, it refuses to act if the image isn't pinned by digest or if a release is half-applied, and it holds the same deploy lock as everything else that touches Compose.

## The deadlock

In October we ran a paid evaluation: 15 real sessions, 45 parent runs. One scenario had an agent delegate to child runs that timed out immediately. It exposed a deadlock we'd built ourselves.

We had work stealing — idle workers could pick up jobs from other queues. Child workers would pick up *parent* jobs. Those parents would then delegate, and wait for children. But the child slots were full of parents. Under saturation, every slot was a parent waiting on a child that had nowhere to run.

The fix was one rule: child workers never lend their slots to parents. Work stealing is still available, off by default, and child capacity is always reserved for children.

## The bug that rejected browsers we had room for

Browser sessions have their own admission, in the browser broker, because each one is a 2 GiB container. The ceiling is the minimum of three numbers: a configured maximum of 32, a share of total host memory, and available memory plus what current sessions are actually using.

For a while, that third number was wrong. Admission took `MemAvailable` — which already excludes what the running sessions use — and then charged each of them their full 2 GiB limit again. Every resident browser was counted twice, and users got "no capacity" with gigabytes free.

The fix credits back only measured anonymous memory from each session's cgroup (never file cache, which the kernel can reclaim), capped per session, and only for this deployment's containers. With eight sessions using 4 GiB in total and 19 GiB available, the ceiling went from 8 to 10. The sampler gets a 1.5-second budget and 0.2-second Docker socket timeouts. If anything fails, it credits nothing — falling back to the conservative answer, not the optimistic one.

## About queue age

Queue age is in our health endpoints — every queue reports its oldest waiting job — and it's the first thing I look at when someone says "the agent is slow". But it doesn't drive scaling, and I've stopped thinking it should on a single machine. Queue age tells you you're *late*. What decides whether you can do anything about it is memory, and memory is a hard ceiling, not a dial.

We're honest about the limits, too. Our pilot ran 12 jobs on 4 workers with about 22 ms p95 to acquire a warm worker and a third of a second to drain. A burst of 250 runs on 16 slots was all admitted in under nine seconds, but took about 490 seconds to clear, against a 120-second target. That's a failed gate, and it's written down as one. The target of a hundred concurrent runs, 25 sandboxes, and 10 browsers on one box is explicitly marked as not yet qualified. Writing that down has been more useful than any dashboard.

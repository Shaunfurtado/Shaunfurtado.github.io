"The agent said it fetched the filing" and "the agent fetched the filing" are different claims. For the first few months of Ananta's agent, our idea of a finished run was mostly the first one. This post is about how we moved to the second, and about the evaluation that showed us where we still weren't.

## Done is decided by evidence, not the model

When a user sends a message, a deterministic planner — not a model — reads the message and the desk state and works out what kinds of evidence a real answer needs:

```python
EVIDENCE_KINDS = (
    "link_fetch",     # the user pasted a URL
    "web_grounding",  # a claim about the world
    "broker_read",    # anything about their holdings or orders
    "calculation",    # a number we have to compute
    "canvas",         # they asked for something on the desk
    "mcp_or_intel",   # market data or research sources
)
```

When the agent says it's finished, a checker walks the run's *audit events* — what tools actually ran and what they returned — not the model's description of what it did. If someone pasted a link and there's no successful fetch of that link, the run isn't done. A calculation done in the model's head doesn't count as a calculation. An artifact request is done when the file exists *and* it's listed for the user.

Some outcomes are legitimately done without the evidence. These are typed blockers: `needs_human`, `action_required`, `source_unreadable`, `url_unreadable`, `policy_denied`, `capacity_exhausted`, `plane_unavailable`. A paywalled page that returns `url_unreadable` is an honest answer. A paragraph that sounds like the page was read is not.

## Nudges have their own budget

If evidence is missing, the harness nudges the agent to continue, up to three times. That budget is separate from provider retries, so a 503 from the model provider can't use up the attempt that was meant to say "please actually fetch the URL".

There's also a repair budget that's harder to fool:

```python
class CompletionRepairBudget:
    def __init__(self, max_unchanged_repairs: int = 1):
        self.limit = max_unchanged_repairs
        self.seen = Counter()

    def allow(self, requirements) -> bool:
        signature = sha256(sorted(pending(requirements)))
        self.seen[signature] += 1
        return self.seen[signature] <= self.limit
```

It hashes the *pending requirements*, not the answer text. An agent that rewrites its prose without verifying anything new hasn't made progress, and gets no second repair. One that verified another source has changed the signature and keeps going.

When the budget runs out, the run completes as `evidence_status=partial`, with a visible strip in the UI saying what couldn't be verified. Hiding that, or failing the whole run, would both be worse.

## The paid evaluation

In early October we ran the agent against the hosted build with real money: 15 sessions written as scenarios, 45 parent runs, 562 provider calls, about 19.85 million input tokens (62.8% from cache), and 372,000 output tokens. Provider-reported cost settled at $0.84, plus $0.22 in reservations that never resolved, against a $5 target and a $10 hard ceiling.

Some numbers were good. Some weren't:

| Measure | Result |
|---|---|
| Median parent run | 177 s |
| p95 parent run | 828 s |
| p95 queue delay (overall) | 1.5 s |
| p95 queue delay (10 follow-ups in a burst) | 111 s |
| 250-job burst on 16 slots | ~490 s to drain, gate was 120 s — **failed** |
| Child runs | 3 completed, 3 partial, 2 timed out, 2 cancelled |

The defects it found were more useful than any of the numbers:

- A comparison mixed **standalone and consolidated** figures for the same company. Both were real numbers, and they weren't comparable. Scope is now a required field when a number is bound to filing data.
- The model **invented a plausible exchange PDF link**. It was withdrawn, and sources now have to be URLs the run actually retrieved.
- A **draft-only request activated a skill override**. Proposals now stay inactive until a person turns them on.
- A **child timed out immediately and borrowed a parent's worker**, which led us to a deadlock in our queues.
- A workflow checklist offered a **configuration sample as proof** that the workflow had actually run.
- **Planning-only mode** used 4 calls, called a tool it shouldn't have, and took 81 seconds. After making tool denial a hard per-turn policy rather than a prompt instruction: 1 call, 0 tools, 19 seconds.

After the fixes, all 16 artifact downloads kept identical hashes across a full runtime replacement — what a user made before a deploy is still byte-for-byte what they get after it.

We also found a bug in the *evaluation's* accounting: the budget settled from the initial stream, but the provider's real cost sometimes arrived later. An audit matched 1,391 call identities. A cost that exceeds its reservation now latches a violation and blocks further admission. An eval harness that misreports spending isn't much of an eval harness.

## What the evaluation didn't measure

It's worth being as clear about this as about the results. These were adaptive sessions with follow-ups, not repeated trials of the same task, so they don't give a reliability distribution. I didn't compute cost per verified completion. Quality scores in our eval records start as `null` and need human review: counting completed runs doesn't tell you whether the answers were good. In our second cycle the full backend suite of 1,709 tests passed, and the same review found a delegated report treating a future-dated daily summary as "today's close". Our notes say plainly that completion status is not a factual-quality pass.

## Paired benchmarks on frozen inputs

For changes that are supposed to save money, we use a paired benchmark. The harness freezes a saved conversation and every successful source-tool output, keyed by tool name and canonical arguments, with a checksum. It replays two variants — for example, full tool attachment versus grouped, on-demand loading — against identical inputs. If a variant asks for a read that isn't in the frozen set, that's an explicit failure. There's no live fallback to quietly make the comparison unequal. Variants run in counterbalanced order, because whichever goes first warms the cache.

A variant is promoted only if, across several cases, it uses at least 25% less cumulative input, adds no more than 10% median latency, and scores at least 4/5 on human-reviewed factual support and presentation, with no capability lost. Reports never promote anything automatically.

Our grouped tool-loading strategy cut schema bytes by 28% and *increased* total input, because it needed extra calls. It wasn't promoted. That's the harness working. It stopped us shipping an optimisation that only looked like one.

The same idea applies to methodology changes. When we test a revised skill, only the skill body differs between variants. Runs on hypothetical data are marked as not qualified on financial sources, so a nice-looking test result can't be mistaken for a research claim.

## The rule I'd keep

For our research delivery gate, there's one line I'd put above everything else: no event is fabricated to turn a true negative into a send. If a workflow couldn't verify its universe, or a source was stale or incomplete, the report is held back and the inbox says why — `universe_coverage_unverified`, `source_publication_stale_or_future`, `source_pagination_incomplete`. One submission and one correction per attempt, then it stops.

An agent that sometimes says "I couldn't verify this" is more useful than one that never does. The evaluation's job is to make sure that when it says it did verify something, it did.

For most of this year I've been the main engineer on the enterprise build of Ananta Market Stack, a trading and market-data workspace that we deploy on the client's own server. There's no shared cloud tenant. Each client gets the whole stack — API, frontend, Redis, workers, a code sandbox, an isolated browser plane, and an agent that can use all of it — running under Docker Compose on a machine they control.

That constraint shaped almost every decision. When something breaks at 2 a.m. on a client's VPS, there is no platform team and no managed queue to blame. The system has to explain itself, recover without guessing, and refuse to do anything it can't account for.

This post is about the unglamorous part: the machinery that decides who owns a run, what happens when a worker dies halfway through, and how we stopped the system from "helpfully" repeating things it shouldn't.

## The model never gets to decide infrastructure questions

The first rule we wrote down sits in the docstring of our plane supervisor: the model never decides whether containers should be restarted, waited on, or replaced.

It sounds obvious. It isn't, once you have an agent with tools like "run Python" and "open a browser". The tempting design is to let the agent see a failure and retry the tool. Then a sandbox broker hiccup turns into three identical code runs, or a browser that was actually still starting gets a second one stacked on top of it.

So every execution plane — sandbox, browser, workers — reports the same small health row (`available`, `runtime`, `reason`, `capabilities`), and recovery is plain code with fixed numbers: three attempts, backoff between 0.35 and 3 seconds, a 20-second readiness timeout, and a circuit that opens after four failures for twenty seconds. When a plane is down, the chat tools fail closed and say so. The agent sees `browser plane unavailable: <reason>`, not a stack trace it might try to reason its way around.

## Topology follows trust, not team boundaries

The stack is one Compose file with profiles. The default profile is deliberately tiny: a bootstrap step that generates secrets on first boot, Redis, the backend, and the frontend. Everything with a larger blast radius is opt-in:

- `sandbox` adds a sandbox broker and a gVisor bootstrap.
- `browser` adds a browser broker and a Squid egress proxy.
- `workers` adds the chat, subagent, workflow, scheduler, and live market-data workers.

Two details in that file carry more weight than they look like they should. Only the two brokers mount the Docker socket — the backend and frontend never do. And the browser network is `internal: true`, so the only way out to the internet from a browser session is through Squid.

We chose Compose plus a small host controller over Kubernetes because each deployment is one client on one large machine. Kubernetes would have handed us scheduling we didn't need and moved the failure modes somewhere the client's IT team couldn't see them.

## Every run has exactly one owner, and ownership can be lost

The core primitive is a small immutable record:

```python
@dataclass(frozen=True)
class RunOwner:
    run_id: str
    attempt_id: str
    epoch: int
    worker_id: str
```

A worker that picks up a run starts a `LeaseKeeper` thread that renews the lease every five seconds. If renewal keeps failing for twenty seconds, the worker stops treating the run as its own. It doesn't try to win it back. An old worker must never adopt an attempt that a successor has already claimed.

The renewal itself is a Lua compare-and-renew in Redis, because the naive version is wrong in a subtle way:

```lua
-- KEYS[1] = lease key, ARGV[1] = owner token, ARGV[2] = ttl ms
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("PEXPIRE", KEYS[1], ARGV[2])
end
return 0
```

With `GET` followed by `EXPIRE` from Python, there is a window in which your lease expires, the next owner takes it, and then your `EXPIRE` lands on *their* lease. You've just extended someone else's ownership on the strength of a stale read. Release is a compare-and-delete for the same reason.

When the worker pool sees a child process exit, it immediately sets `lease_expires_at = now` on that child's running runs, so the next worker doesn't have to wait out a TTL to take over. We only do this when we actually observe the exit. Missing metadata in Redis is not treated as death — that was a lesson from a Redis restart that made several healthy workers look dead.

## Retries belong to the application

We call the model provider's SDK with `max_retries=0`. All retries are ours.

That came from a specific failure. A provider returned a quota error with a `Retry-After` that was hours long, and the SDK, quite reasonably from its point of view, honoured it — inside a job with a 600-second timeout. The run sat there doing nothing until the job was killed, and the user saw a spinner followed by a generic timeout.

Our retry policy classifies failures first: transient transport, rate limited, quota exhausted, unknown tool, repeated tool call, unpaired tool results, and a few more. Each class gets its own treatment. The defaults are three retries (a user can raise it to eight), 2–12 seconds of backoff, a cap of 60 seconds on any server-requested delay, and a 75-second limit on an idle stream. Quota exhaustion isn't retried at all. It becomes a clear message.

## An uncertain outcome becomes a receipt

This is the idea I'd keep if I had to throw the rest away.

When a worker dies, some calls are in a state nobody can resolve from the inside. A model call was dispatched but no usage event came back. A browser was asked to start and the client got an HTTP 499, but the container may well be running. In each case the tempting move is to retry, and in each case retrying can double the effect.

We don't. An interrupted model call becomes a visible "unavailable" entry in the run's ledger. A recovery ledger carries the *accepted* results and the exact resource and call identities across a crash, so the next attempt can continue from facts. Its own docstring is blunt about its limits: it cannot make an interrupted mutation safe to repeat.

Reads are different. Inside a run, a read can be replayed, with one in-flight call per read. A successful write bumps a per-domain epoch (workflows, watchlists, skills, workspace, external), so a read → edit → verify sequence isn't mistaken for the agent going round in circles.

## Two incidents that changed the code

**Transactions held across model waits.** In early October we found the runner holding SQL read transactions open while it waited on sandbox and browser health checks and MCP teardown — calls that can take seconds. The fix had a trap in it. Rolling back expires ORM objects, so the next time anything touched a field on the run, SQLAlchemy quietly opened a *new* transaction, this time from the SDK's concurrent task. We ended up committing clean reads with `expire_on_commit=False` and rolling back only when the session was actually dirty. We proved it with a real pool of exactly one connection and zero overflow: any leaked transaction deadlocks immediately, which is a much better test than hoping a bigger pool hides it.

**A deploy racing the capacity controller.** A rollout failed with a "missing container" because the host capacity controller was resizing workers at the same moment. Then a recovery command was started before the failing Compose command had exited, which made the name conflicts worse. Now every component that touches Compose — deploy, redeploy, browser image sync, the resizer — takes the same exclusive `flock`. We also wrote down a rule that felt silly until we needed it: always wait for a command's process to exit before starting the command that's supposed to recover from it.

## What "deterministic" means here

It doesn't mean nothing fails. Workers die, providers rate-limit, Docker Desktop does strange things with volumes. It means that for any run we can answer three questions from stored state, not from logs and guesswork: who owned it, which effects were accepted, and which outcomes are still unknown.

If we can't answer the third question, the system says "unknown" to the user instead of picking whichever answer looks better. That one rule has prevented more bad outcomes than any amount of clever retry logic.

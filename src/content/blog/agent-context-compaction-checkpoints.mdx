Analysts keep Ananta chats open for days. One conversation might cover a results season: pull quarterly numbers for five companies, compare margins, build a canvas, set an alert, come back two days later and ask "what did we conclude about the second one?"

Until September our answer to long chats was a blunt cap: the last 20 turns, text only. It was predictable, and it forgot exactly the things people came back for. This post is about what replaced it, including one place where I deliberately chose the less safe option.

## When compaction runs

Budgets are in characters, not tokens, with a rough four-characters-per-token estimate for reporting. It's an approximation and the code says so. The defaults:

```python
MODEL_INPUT_CHAR_BUDGET = 120_000
COMPACT_RESERVE_CHARS = 12_000
COMPACT_KEEP_RECENT_CHARS = 20_000
COMPACT_SUMMARY_MAX_CHARS = 3_500
COMPACT_ANXIETY_RATIO = 0.80
```

Compaction triggers at 80% of the budget minus the reserve — before the window is full, not when it overflows. The projection includes the context hooks and status bar, since those count too. For self-hosted models the budget comes from the model's declared context window, minus reserved output, instructions, and the estimated size of the tool schemas.

## What it does

1. **Keep recent turns raw.** Walk backwards from the newest turn and keep whole turns — user message, assistant reply, and tool digest together — until 20,000 characters are used. The cut always lands on a turn boundary, never inside one.
2. **Clear older tool output.** Older tool digests are replaced with a placeholder telling the model that prior tool results were cleared and that `session_search` and `session_expand` can bring them back.
3. **Summarise the middle.** A cheap model writes a structured summary of everything older than the recent window, with the previous summary passed in to be merged rather than rewritten from scratch.

The summariser prompt has fixed sections — Symbols, Facts, Numbers, URLs, Canvases, Blockers, Open threads — and a few hard rules: list only facts present in the source; never invent prices, ratios, holdings, URLs, or canvas ids; never include keys, tokens, or OTP codes. The output then goes through a regex pass that redacts anything shaped like a key, in case the rule didn't hold. Temperature is 0.1, and input to the summariser is capped at 48,000 characters.

The summary is stored on the session row with the id of the first run it didn't cover. It's prefixed with a marker saying it's a compressed summary not shown to the user. Audit events and the search index are never touched — compaction changes what the model sees, not what the system remembers.

## Which model writes the summary

The summariser is chosen in order: an explicitly configured compaction model; otherwise an allowed model whose name suggests it's small (flash, mini, haiku, lite, and so on); otherwise the chat model itself.

Every candidate has to pass the same inference policy check as a normal chat call. That closed a review finding in October. If a workspace is set to keep confidential content on self-hosted models, compaction mustn't be the side door that sends a summary of that content to a cloud model just because it's cheaper. A summary of confidential material is still confidential material.

## The choice I made differently from the textbook

The textbook answer — I wrote a version of it myself in an earlier draft of this post — is that a failed or empty summary should never advance history. If you can't summarise the older turns, you shouldn't drop them.

Ananta does drop them. If the summariser returns nothing and a previous summary exists, we keep the frozen previous summary and still move the recent window forward. If the summariser throws, we use the frozen summary plus recent turns. With no previous summary, we drop the oldest turns until things fit, and record `fallback: drop_oldest` in the audit log. In each case, turns between the old summary and the new recent window disappear from the model's view.

We chose that because the alternative is worse for the person using it. A summariser timeout (we allow 45 seconds) would otherwise fail their chat turn, or leave every future turn too large to send. Compaction never fails a run. It's lossy, the run proceeds, and the loss is recoverable because nothing is deleted — the agent can search for what fell out.

I'm comfortable with that trade because of the next section. Without it, I wouldn't be.

## Recall is the other half

Two tools let the agent reach back into history: `session_search` and `session_expand`. Search uses SQLite FTS5, or a search table on Postgres, with optional hybrid retrieval that fuses a small embedding model's results with full-text results using reciprocal rank fusion. Embeddings are off by default. If they fail, search falls back to full text alone.

The defaults are lean on purpose. Search returns five hit cards with no surrounding context. Expanding a hit allows a radius of at most eight events and 6,000 characters. Each indexed event is capped at 4,000 characters, with secrets stripped before indexing. The tool's description tells the agent to expand at most twice per turn, and to re-fetch the original source if the result is still truncated.

The first version of recall wasn't good. Search windows came back full of `[response_completed]` placeholders, and queries matched bare `run_started` events. We changed the default window to zero, made expand return only evidence-bearing events, ranked hits from the current run lower, and added stop words to the full-text index. Search also stays in its lane: this chat, or one explicitly named session the user owns. Results say that zero hits don't prove something isn't in another session.

One more thing came out of the design discussion: summary facts are *weak evidence*. If a number from the summary is going into the current answer, the agent is expected to expand the original or fetch it again. A summary is a pointer to where to look, not a source to quote.

## Not every run should see history

The worst compaction-related bug we had wasn't about compaction quality. In early October a scheduled analysis overstated a block trade, because scheduled runs were inheriting older conversation answers and workflow-editing chatter through history and its summary. The run was mixing what someone had discussed with what the data said.

Scheduled and alert-triggered runs now execute with no prior turns at all. On that workflow, context went from 12 turns, 197 tool projections, and about 154,000 characters to zero turns and about 36,000 characters. Cost dropped too, though that wasn't a controlled comparison and I don't quote it as one. A few days later we found workflow compaction had dropped a workflow's active period, so the agent missed which days it was eligible to run. Schedule, calendar eligibility, and delivery policy are now kept separately from the large targeting payload, so they survive even when that payload is trimmed.

## What I'd still change

Coverage could be tighter. Under the threshold, the stored summary is prepended to the normal recent history, and depending on where the last compaction landed, the two can overlap a little. It costs a few characters, not correctness. We also count characters instead of tokens, which is fine for one provider and loose for others.

What I wouldn't change is the split: an audit log that keeps everything, a model view that keeps very little, and a search tool between them. That split is what lets the summariser be imperfect.

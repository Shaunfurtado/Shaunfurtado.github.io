The case for subagents in Ananta is narrow. Someone asks the agent to compare two companies' annual results. Each company means a filing to find, a few hundred pages to read selectively, and numbers to extract with their scope — standalone or consolidated — checked. Doing both inside one conversation fills the context with two filings' worth of evidence before any comparison happens.

So the parent delegates: one child per company, each with a clean context, each returning a structured result. The parent does the comparison. Here's how that's built, and the one design decision I reversed within three weeks.

## One generation, gated by skills

Children are generation 1. The parent is generation 0. Any spawn request from a non-zero generation is rejected with `generation_forbidden`, and children never get the spawn tools anyway. No grandchildren, no agent-to-agent protocol, no peer networks. Those are written down as non-goals.

A parent can't spawn just because a model decides it would be nice. Spawning is declared by a skill. A skill such as delegated source review carries a block in its frontmatter:

```yaml
spawn:
  mode: isolated_child
  max_fanout: 4
  max_concurrency: 4
```

On top of that, every `subagent_*` tool needs the `research.deep` permission, and there's an optional per-member daily limit on deep research, reserved idempotently so a retry doesn't count twice.

## Durable children

The parent gets three tools: `subagent_run`, `subagent_status`, and `subagent_cancel`. A spawn waits at most 15 seconds. If the child hasn't finished, the parent gets a persisted handle and polls.

Each child is a row in an `agent_subruns` table with a lease, a heartbeat, an attempt, and an idempotency key derived from the task. States: submitted, queued, running, needs input, completed, partial, failed, cancel requested, cancelled, timed out. Cancelling the parent cascades to its children. On startup, reconciliation re-queues only work that is safe to re-run.

Running out of capacity isn't an error. `subagent_run` returns `status: "capacity_reached"` as a normal result, and the parent can do the work itself or wait. That change came from watching agents treat capacity errors as failures and give up on the whole task.

## The child doesn't get the transcript

The function that builds a child's context has no parameter for the parent's conversation. That's by design, not an oversight. A child gets a short system prefix, one typed task envelope, the skill body, and only the context hooks the skill lists — at most eight.

```json
{
  "objective": "Extract FY26 and FY25 consolidated revenue and PAT from the annual report",
  "acceptance": {
    "required_evidence": 1,
    "output_schema": "source_review.v1",
    "environment_checks": []
  },
  "inputs": { "company": "INFY", "period": "FY26" },
  "artifact_refs": [],
  "parent": { "run_id": "…", "workspace_version": 41 }
}
```

The transcript stays out because it's mostly noise for a narrow task, and because it's where the parent's half-formed conclusions live. A child that reads "I think margins fell" in the parent's history tends to find margins falling.

## A result has to carry evidence

When a child finishes, its result is validated before the parent sees it. The output must match the declared schema. A `completed` result must have at least the required number of evidence references marked valid, at least one finding, and every declared environment check. Partial and failed results are accepted as partial or failed, so the parent can merge what was done. The digest the parent receives is a deterministic projection of the result, not another model's summary of it.

One early failure: children returned perfectly reasonable prose that failed the structured contract every time. The fix was simply to show children the exact JSON result shape in their instructions. After that, a child reviewing an SEC filing came back with three findings, each tied to a source.

## The reversal: from allowlist to denylist

The first version, in early September, was strict. Children ran against a hard allowlist of about 24 read-only tools. Effective tools were the intersection of the skill's list, the user's permissions, what was available at runtime, the hard allowlist, and what the parent requested. Each child had fixed ceilings: 8 turns, 90 seconds, 30,000 input tokens, 3 web fetches, 24 tool calls, $2. The policy file's comment said it was deliberately an allowlist, not a denylist.

Three weeks later we rewrote it. A skill's tool list is now a routing hint, not a fence. Children get every tool available at runtime, filtered by the user's permissions, *minus* a parent-only list: spawning, proposing or activating skills, proposing or enabling extensions, composing or publishing canvases, and plan management. Per-child budgets became observability counters. Zero means unlimited, and the runtime doesn't enforce them as ceilings.

```python
effective = set(runtime_tools)
if authorized:
    effective &= authorized
effective -= PARENT_ONLY_TOOLS   # spawn, skills, extensions, canvas, publish, plans
```

In practice the strict version kept starving children. Real source reviews needed tools that weren't on the list, and the fixed ceilings ran out before the work did, so children timed out or came back partial. The change landed together with a batch of stability fixes: recovering malformed delegated tool calls, treating capacity as a normal result, and preserving partial work.

What didn't change is what actually bounds a child: the permission check that wraps every tool call and runs fresh each time, run-level gates on tool calls, model calls, and reserved tokens, a breaker for identical repeated calls, deadlines, and the monthly spend limit. A child can't publish, can't change skills, can't spawn, and can't do anything the user couldn't. Children also get the user's connector read tools but never write-backs, because write-backs need an interactive confirmation and a child has no one to ask.

I still think "delegate work, not authority" is right. I just learned that authority lives in the permission check on each call, not in how short you make the child's tool list.

## What the evaluation showed

Our October paid evaluation had ten child runs: three completed, three partial, two timed out, two cancelled. Not a great scorecard, but each failure pointed at something concrete.

- **A deadlock.** Parents wait for children while holding a worker. With work stealing, child workers picked up parent jobs. Under load, every slot held a parent waiting for a child with nowhere to run. Child workers now serve only the child queue.
- **Polling killed by our own breaker.** The repeated-identical-call breaker (two identical calls and you're stopped) was killing parents that were legitimately polling `subagent_status`. Delegation waits are now exempt from that check but still count towards the overall tool-call limit, and the default wait went from 5 to 15 seconds.
- **Misleading cost.** Child cost was taken from SDK reports, which were missing for some calls. It's now projected from our own call records, including retries and cancellations, and interrupted children keep their charges. Missing cost is never read as free.

When it works, it works the way I hoped. In the acceptance run, two isolated children reviewed one company's FY26 and FY25 reports. The parent computed year-on-year growth from their two numbers — (178,650 − 162,990) / 162,990 = 9.61% — and the user's follow-up question was answered with zero further tool calls, because the evidence was already structured.

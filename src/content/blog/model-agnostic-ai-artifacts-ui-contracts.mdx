The adaptive workspace is the part of Ananta people demo first. Ask for "a desk for my IT holdings with a results calendar", and the agent lays out a holdings table, a price chart, an earnings comparison, and some notes on a grid. Ask it to move the chart or add an option chain, and it edits the layout.

What it never does is write React, HTML, or CSS for that desk. It writes a spec, and our code decides what that spec is allowed to mean.

## The spec

A `WorkspaceSpec` is a Pydantic model with `extra="forbid"` on every level. Version 1 has a 12-column grid, components at most 24 rows tall, and about 22 allowlisted component types: `holdings-table`, `quote-chart`, `option-chain`, `notes-block`, and so on.

```python
class WorkspaceComponent(BaseModel):
    model_config = ConfigDict(extra="forbid")
    id: str = Field(pattern=r"^[a-z][a-z0-9-]*$")
    type: ComponentType              # one of the allowlisted types
    position: GridPosition           # x + w <= 12, h <= 24
    data: DataRef | None = None      # {tool, params}, not a dataset
    props: dict[str, Any] = {}
    actions: list[ActionName] = []   # allowlisted semantic actions
```

Two decisions make this safe.

**Data is a reference, not a payload.** A component's `data` field names an allowlisted data tool and its parameters — "holdings for this account", "quotes for these symbols". The frontend fetches it through the normal authenticated API. The model can't paste numbers into a table and have them look like broker data. Parameters with secret-shaped keys (`api_key`, `password`, `pin`, `totp`, `token`) are rejected.

**Props can't carry code or styling.** `className`, `style`, `css`, `dangerouslySetInnerHTML`, `innerHTML`, `jsx`, `children`, `href`, `src`, and `onClick` are forbidden. Behaviour goes through named actions the frontend implements. The frontend also validates the spec again and fails closed on the same rules, so a bug on one side doesn't open the other.

Overlapping widgets aren't rejected — models are bad at grid arithmetic — they're packed downward.

## An invalid spec is a result, not an error

The agent edits the canvas with `compose_surface` (whole layout) and `patch_surface` (replace, add, remove, duplicate, move, update, retitle). It can dry-run with `workspace_validate_spec`.

When a compose or patch is invalid, the tool doesn't raise:

```python
return {
    "ok": True,
    "applied": False,
    "valid": False,
    "validation": {"errors": errors},
    "hint": "Fix the listed fields once and retry.",
}
```

We made that change in August so the model could correct itself without a retry loop. An exception looks to the agent like the tool is broken, and it tries something drastic or gives up. A result with `applied: false` and specific errors looks like feedback, and it fixes the field. Every applied change is saved as a versioned snapshot, and restoring a canvas uses the latest snapshot, not a replay of the chat.

Canvas tools only exist when the instance has the adaptive workspace enabled and the run is a workspace run. The classic chat page never sees them.

## Finance tables have to cite things

For research output there's a typed finance canvas: earnings comparison, catalyst timeline, movers and breadth, scenario calculator, evidence table, and changes. Tables have 1–8 columns, at most 40 rows, at most 20 sources, and cells of at most 500 characters. Every row points at a source index.

A source has to be one of three things: an exact HTTP(S) URL that was actually retrieved in this run, a saved document, or a *tool receipt* — the 36-character id of a successful tool event owned by the same run, which the server looks up. The model can't cite a URL it never fetched.

Numeric cells can go further. A metric binding names the symbol, standalone or consolidated scope, period, metric, unit, and multiplier, and the server checks the value against structured filing data. The result says how many cells were bound and checked, and labels the rest `not_fact_checked`. We'd rather say outright that the prose isn't verified than suggest the whole table is.

That labelling has a story behind it. An evaluation run mixed standalone and consolidated figures in one comparison — both real numbers, from the same company, and not comparable. Scope is now a required field on a binding, and the rule is never to mix them.

## The HTML escape hatch

Some things don't fit a catalogue. So there's an `html-artifact` component, with tighter rules than anything else.

The backend rejects iframes, `javascript:` URLs, `meta http-equiv`, and remote scripts, stylesheets, and images, and caps the document at 60,000 characters. The frontend then strips *every* authored `<script>` and `<style>` and wraps what's left in a host-owned kit with our own styles and a small set of behaviours. External links in citations are parsed, limited to 20 unique URLs per change, and each one is checked against the run's source ledger. The result runs in a sandboxed iframe without `allow-same-origin`.

That kit caused our most instructive bug. In an October evaluation, a generated scenario calculator had sliders that moved while the numbers stayed put. The model had put the calculation handler in a `<script>`, which the kit strips, as designed. The fix wasn't to allow scripts. We moved bounded arithmetic into the host kit itself, driven by numeric data attributes the model can write: base value, rate, percentage. Saved calculators were repaired on reload without a paid regeneration. The test case: 10,000 × 1.05 × 22% = 2,310.

## Error messages are part of the contract

Two more fixes from October were really about what we tell the model.

A projection canvas failed three times in a row on a source the agent couldn't identify, because every error repeated the full list of source rules. Now the error names the failing field and lists the receipt ids the run can actually use.

And after publishing an HTML artifact, the agent usually stopped — so the desk stayed empty while the run counted the canvas as published. Publishing now places the canvas on the desk by default. The model's idea of "done" and the user's idea of "done" have to be the same state in the code, not two states we hope line up.

## What "model-agnostic" means here

None of this depends on which model is driving. A smaller model makes more invalid specs and gets more `applied: false` results back. A larger one gets it right first time more often. Both end up rendering through the same components, with the same source checks, the same snapshots, and the same sanitiser. The contract is what we test. The model is just whoever is writing to it this week.

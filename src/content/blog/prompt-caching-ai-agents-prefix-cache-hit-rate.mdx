An agent turn in Ananta can involve a dozen model calls, and every one of them resends the system prompt and the tool definitions. With the full tool catalogue attached, that's tens of kilobytes per call before the user's question even appears. Provider-side prompt caching is what makes that affordable, and for a while we were accidentally defeating it with code that looked like good hygiene.

## The evaluation

In early October we ran a paid evaluation on the hosted build: 15 real sessions, 45 parent runs, 562 provider calls, all through one OpenRouter-routed model. About 19.85 million input tokens in total, of which 62.8% were served from cache. The settled cost was $0.84, plus about $0.22 in reservations that never resolved — because 9 calls never reported usage at all.

That 62.8% hides the story. Here's cache coverage by phase:

| Phase | Cache coverage |
|---|---:|
| First runs, full tool catalogue | 21.0% |
| "Optimised" selective tool loading | 10.9% |
| Stable tool order + prefix affinity | 78.8% |
| Final image | 85.3% |

The optimisation made things worse — it halved cache coverage.

## The cause

Selective loading means the agent starts with a smaller set of tools and loads more as it needs them (I wrote about how that works in [the skills and tool visibility post](/blog/skills-adaptive-tool-visibility-agent-authorization/)). Loaded tools are appended to the list. That should be cache-friendly: the prefix up to the old last tool stays the same.

But our provider audit transport — the layer that logs and forwards requests — was doing this on every request:

```python
# before
body["tools"] = sorted(body["tools"], key=lambda t: (t["type"], t["function"]["name"]))
```

It was there so request logs would be deterministic and easy to diff. With a fixed tool list, it was harmless. With tools loaded on demand, a newly loaded tool whose name sorted near the front shifted every tool after it. The cached prefix ended right at the first tool — every time the agent loaded something.

The fix removed the sort and left a comment where it used to be: the capability catalogue already produces a deterministic, append-only order, and re-sorting would invalidate an accepted prefix after a tool load.

We also started sending a prompt cache key — a hash of the model plus the system messages — as a routing hint, so requests with the same prefix are more likely to land on a provider instance that already has it cached. The code says plainly that it's a hint, not a guarantee, and that observed usage is what counts.

## Keeping the prefix stable on purpose

Fixing one bug doesn't stop the next one. A few rules now hold the prefix together.

**Everything dynamic goes at the end.** The current date, context hooks, loaded skill bodies, and the status bar are appended as trailing messages, never written into the system prompt. A clock in the system prompt is the classic cache breaker — the prefix changes every minute.

**A lint for the obvious mistakes.** Before every call, the harness checks the system instructions for markers that should never be there — `Today is`, a dumped workspace spec, a selected canvas component id, connected MCP context — and records a cache breaker if it finds one.

**Compaction is the one planned break.** When a conversation is summarised, the history prefix changes. So the summary is stored and reused until the conversation crosses the threshold again, rather than regenerated on every turn.

## Measuring it per call

For every model call we record the byte size and SHA-256 of each component: system messages, tools (both sorted and in their actual order — comparing the two would have caught our bug immediately), history, each message, and parameters. We also hash the raw request bytes at 256, 4,096, 16,384, and 65,536 bytes, which tells us roughly how far into the request two calls agree.

A per-run tracker compares each call with the previous one:

```python
{
  "instructions_changed": False,
  "tools_changed": False,           # order-sensitive
  "matching_leading_messages": 14,
  "history_prefix_rewritten": False,
  "history_shortened": False,
}
```

It's labelled as local message hashes, not tokeniser or provider cache accounting. It tells you whether you *offered* the provider a stable prefix. Whether the provider *used* it is a separate number, read from usage.

## Missing isn't zero

Providers report cached tokens under different field names, and sometimes not at all. Our usage records normalise the variants and keep a separate flag saying whether cached tokens were reported. A call with no cache data is *unreported*, not a 0% hit and not a 100% hit. Nine calls in that evaluation fell into that bucket, and folding them in either way would have moved the headline number.

## Why I won't quote one savings figure

You could price the same observed tokens as if nothing had been cached and compare. For that evaluation it comes to about $2.06 without caching against $0.84 actual — roughly 59% less. Our write-up includes that number with a warning attached: it's specific to that model and that price list, and it isn't proof that our code changes alone reduced spending.

Per-session cache coverage ranged from 0.3% to 93.6%. A short one-question session never warms the cache. A long research session with a stable prefix lives in it. Any single average describes neither.

## What we didn't ship

Selective tool loading did cut the median serialised tool payload by about a third in bytes (not the same thing as tokens). It's still not the production default. A paired benchmark on frozen inputs showed the deferred strategy needing extra calls to discover and load tools, so total input went *up* slightly while latency rose. Our promotion gate asks for at least 25% less input with no more than 10% extra latency, and it wasn't met.

So production attaches the full tool list for the selected route, in a stable order, and the cache does the rest. It's less clever than what I'd planned. It's also cheaper — and we can show why.
